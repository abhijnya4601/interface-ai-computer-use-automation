Discover once, replay forever

An AI learns a banking task once, by actually doing it — then the system replays that exact recipe forever, deterministically, with zero AI involved after that first run.

Built for interface.ai — the take-home core, then adapted live against MERIDIAN CORE.

Act 1

The take-home core

Eight modules. Each is a short write-up — what it is, the tool it uses, why that tool and not the obvious alternative — followed by a flowchart of its control flow, the scripts that exercise it, and, where there was one, a real bug found while building it.

Perception

Perception turns the live page into something the agent can reason about — not a screenshot, but the browser's own accessibility tree. It returns YAML: every element's role, its accessible name, its current value, and its children, in document order. This is a standard Playwright capability, not something the project built.

page.locator("html").aria_snapshot() Walks the same structured accessibility tree a screen reader exposes to a blind user, and serialises it. A live, synchronous call — it reflects dynamic and JS-rendered content at the moment it runs.

A screenshot plus a vision model was the obvious alternative, and was rejected: pixel coordinates break the instant a page reflows or restyles, and a vision model has to infer what a shape means rather than read a declared identity. A raw DOM query with custom heuristics was rejected too — it reinvents what the browser's accessibility engine already resolves correctly, ARIA overrides included. Fixed-coordinate record-and-replay tools have no resilience to visual change at all.

The approach also degrades well on messy markup: an element with no explicit ARIA role still gets an implicit one from its HTML tag, so ordinary semantic-but-untidy HTML is handled far better than a CSS-selector scraper would manage. Its real limit is an element with no accessible name at all — which is exactly where Act 2 begins.

flowchart TD
    A[Live page] --> B[aria_snapshot]
    B --> C{Any iframes?}
    C -->|no| E[role/name tree]
    C -->|yes| D[Snapshot each frame separately, graft in as synthetic Iframe node]
    D --> E
    E --> F[Passed to discovery loop as observation]

Real bug found here

The spec called for page.accessibility.snapshot(); it no longer exists in the Playwright version used. Its replacement, aria_snapshot(), was verified against a live page and found to not reach inside iframes at all — confirmed by testing, not assumed. Fixed by snapshotting each iframe separately and grafting the result in under a node deliberately capitalised (Iframe) so nothing downstream mistakes it for a real accessibility role the page declared.

Discovery loop

The discovery loop is where a task is actually learned. Given a goal in plain English, Claude — via the Anthropic API — drives a perceive / decide / act cycle: read the current observation, choose the next action, run a guardrail check before anything executes, let the recorder log the accepted step, and repeat, until the goal is met, a step or time limit is hit, or the agent is stuck.

An LLM is used here, and only here, because this is the one place that needs judgment — "there are two Continue buttons, which one" is not something you can hardcode. Hand-writing the steps instead would mean rewriting them per task and breaking on any page change; letting the agent discover them is what lets it handle a page it has never seen. When it can't make progress, it doesn't loop or hallucinate — it detects repeated identical observations and escalates to a human.

flowchart TD
    A[Goal + observation] --> B[Claude decides next action]
    B --> C[guardrail_check before executing]
    C -->|blocked| X[GuardrailViolation, halt]
    C -->|allowed| D[Execute via agent/tools.py]
    D --> E[Recorder logs the step inline]
    E --> F{Finished, max_steps, timeout, or dead-end?}
    F -->|no| A
    F -->|dead-end detected| G[Auto-escalate to human]
    F -->|yes| H[Discovery complete]

Recorder

The recorder runs inline during discovery, writing each accepted action as a precise step — and, crucially, recording how the element was found, not just what was done to it. It's plain Python: a four-tier fallback locator builder that tries a unique role-plus-name match first, then first-of-many, then raw text, then position within a table.

Four tiers exist because real pages aren't uniformly labelled — a single rigid strategy fails outright on the cases the weaker tiers are there for. Always using the strongest match isn't an option, because it doesn't always exist. Every step records which tier produced it, and that log is the drift signal used later.

flowchart TD
    A[Element to record] --> B{role+name match count}
    B -->|exactly 1| C[Tier: role_name]
    B -->|more than 1| D[Tier: structural - first match]
    B -->|0| E[Tier: text - raw text match]
    F[Special case: table cell, no per-row label] --> G[Tier: table_position]
    C & D & E & G --> H[Logged to tier_log - the drift signal]

Capability schema

A saved recipe is a typed, versioned JSON document — built and validated with Pydantic, not written as code. Each step carries its locator strategy and a human-readable reason; the capability carries its expected outcomes, a risk level, and input/output schemas.

Pydantic rather than a plain dict, because a bare dict lets anything through unchecked. In a banking system a silently malformed artifact is far worse than an immediate, loud validation error at load time.

flowchart TD
    A[Capability] --> B[Steps list]
    B --> C[LocatorTarget: strategy + reasoning - required, not optional]
    B --> D[ExpectedOutcome: business_outcome / recoverable / hard_failure]
    A --> E[risk_level: safe or risky]
    A --> F[input_schema / output_schema]

This is a schema definition (artifact/schema.py), not a runnable script, so it has no scripts of its own.

Compiler

The compiler finalises a raw recording into that schema and attaches the known business outcomes for each step — drawn from actually exploring the app, not from whatever a single discovery run happened to encounter.

Outcomes are declared here, at build time, rather than guessed at replay time, so that replay never has to interpret a page live — it already knows what each result means.

flowchart TD
    A[Raw recorded steps] --> B[Attach known outcome rules per step]
    B --> C[save_capability writes capabilities/id.vN.json]
Real bug found here

An outcome was originally declared on the wrong step — it assumed a locked-member denial happened at the "Continue" click, when the app actually never renders that link at all for a locked member, one click earlier. Found by replaying every declared outcome against the real app, not by trusting the original assumption.

Replay engine

The replay engine runs a saved recipe against new input, deterministically. It uses Playwright and imports no LLM anywhere. For each step it walks the same four locator tiers in order, executes the action, then checks the step's declared outcomes.

This is the core of the architecture: the same input produces the same steps and the same checks every time — fast, and free of AI cost or variance. A matched outcome resolves to a business result or a recoverable one; an unmatched result is a success only if a checkpoint verified, otherwise a hard failure with a screenshot. Nothing is guessed.

flowchart TD
    A[Step to execute] --> B[Try tier 1: role_name]
    B -->|fail| C[Try tier 2: structural]
    C -->|fail| D[Try tier 3: text]
    D -->|fail| E[Try tier 4: table_position, if applicable]
    E -->|fail| F[No element found]
    B -->|found| G[Execute action]
    C -->|found| G
    D -->|found| G
    E -->|found| G
    G --> H{Check declared expected_outcomes}
    F --> H
    H -->|matched, business| I[Result: business_outcome]
    H -->|matched, recoverable| J[Result: recoverable_handled]
    H -->|no match, checkpoint verified| K[Result: success]
    H -->|no match, nothing verified| L[Result: hard_failure + screenshot]

Guardrails

Guardrails are three independent mechanisms: an allowlist checked before every action (domain, action type, route), a redaction pass over anything headed for disk (by key name and by value shape), and encryption at rest.

The encryption uses the audited cryptography library rather than anything hand-rolled — writing your own crypto primitives is one of the most common serious mistakes in security. The allowlist and redaction pass are the project's own code, deliberately small.

flowchart TD
    A[Proposed action] --> B{Domain allowed?}
    B -->|no| X1[GuardrailViolation, halt]
    B -->|yes| C{Action type allowed?}
    C -->|no| X1
    C -->|yes| D{Route blocked?}
    D -->|yes| X1
    D -->|no| E[Action proceeds]
    E --> F[Result about to be written]
    F --> G[redact by key name]
    G --> H[redact by value shape]
    H --> I[encrypt_at_rest, if configured]
    I --> J[Written to evidence/]

Escalation

Escalation is the hand-off: a risky checkpoint or a stuck agent pauses and waits for a human to approve or decline before anything irreversible happens. The mechanism is a shared lease file — exactly one of {automation, human} holds control — plus a separate Flask console, behind auth, where the reviewer sees the saved screenshot and context.

An approval flips the lease back and resumes the same browser session; a decline ends the run with nothing committed. The AI doesn't get to make this call, because some banking actions can't be undone.

flowchart TD
    A[Risky checkpoint or dead-end] --> B[Flip lease to human, screenshot + context saved]
    B --> C[Operator console shows context]
    C --> D{Human decision}
    D -->|approved| E[Flip lease back, resume same browser session]
    D -->|declined| F[Result: escalated, nothing committed]

Act 2

The MERIDIAN adaptation

Point the same core at a real, messy legacy target — web-sample.interface-hiring.com — cover its full function surface, and wrap it as a callable API a chatbot drives and a dashboard shows. The schema didn't change. Six modules, same shape as Act 1.

The blocker

aria_snapshot() still runs fine against MERIDIAN — it's a standard browser API and nothing about the target breaks it. What breaks is what it returns. MERIDIAN's forms put the label in a neighbouring table cell — <td class="lbl">Amount:</td><td><input name="amt"></td> — with no programmatic association (<label for>, aria-label, aria-labelledby) to the input. The accessibility engine has nothing to name the field from, so the snapshot honestly reports an unnamed textbox.

Perception itself didn't change. What broke is one layer down: locator tiers 1–2, which assume role-plus-name resolves to something. This was confirmed live, not assumed — a query for a textbox named "Operator ID" on the sign-on page returned zero matches, on a field a human reads instantly.

Three obvious escapes were rejected. Screenshots plus a vision model reintroduce exactly the fragility Act 1 chose the accessibility tree to avoid — pixel coordinates on a table-based legacy layout are the worst case, not a reasonable exception. Hardcoded CSS selectors per field are brittle and defeat the "discover it, don't hand-write it" premise. Asking MERIDIAN's maintainers to add labels isn't an option against a fixed target you don't control.

flowchart TD
    A[MERIDIAN input field] --> B[aria_snapshot - unchanged, still live]
    B --> C[Unnamed textbox - browser has nothing to name it from]
    C --> D[Tier 1 role_name: 0 matches]
    D --> E[Tier 2 structural: 0 matches]
    E --> F[Perception itself is fine - the locator ladder needs new rungs]

New locator tiers — legacy_locate.py

The fix is two functions added to the existing ladder as tiers 3 and 4. Nothing in tiers 1–2, the schema, or the replay engine's control flow was rewritten — it's strictly additive.

Tier 3 (derive_unnamed_field_labels() + locate_labeled_field()) runs a small JavaScript snippet in the page via page.evaluate(). For each unnamed control it looks at what's physically next to it — a labelled cell in the same row first, then a preceding cell's text, then a loose <label> — normalises whitespace, strips a leading * or trailing :, and matches the derived label back to exactly one control. It runs in-page rather than parsing a serialised tree in Python because it needs live DOM relationships (closest(), previousElementSibling) the way a human eye tracks across a row. A model trained to guess labels from layout was rejected as non-deterministic and unnecessary — the structure already holds the answer. It runs fresh on every observation, so it tracks the row currently on screen, and it refuses to guess: a label matching more than one control is dropped for a looser candidate.

Tier 4 (locate_field_name()) resolves a control by its raw HTML name= attribute — the actual HTTP form contract the server needs, so it's load-bearing, not a hack. It's ranked last despite arguably being the most stable of the four, because name="amt" is opaque to a human reviewer and reviewability is a principle worth keeping.

flowchart TD
    A[Unnamed control] --> B[Tier 3: labeled_field - nearest label cell/text]
    B -->|ambiguous or none| C[Tier 4: field_name - the HTML name attribute]
    C -->|ambiguous or none| D[Tier 5: table_position / text, same as take-home]
    B -->|exactly 1 match| E[Resolved, logged to tier_log same as every other tier]
    C -->|exactly 1 match| E

Sessions — session.py

MERIDIAN needs a sign-on, and its sessions idle-timeout — neither of which the take-home needed. Sign-on is handled as just another recorded capability: no special path, credentials passed as typed parameters, never baked into the artifact.

run_with_session replays sign-on first on the same browser page, then the target capability. A bad password comes back as an ordinary business outcome; a session that expires mid-flow triggers one re-login and a retry of the step.

flowchart TD
    A[Invoke a session-gated capability] --> B[Replay meridian_signon first, same browser]
    B --> C{Signon result}
    C -->|business_outcome, e.g. bad credentials| D[Return that result directly]
    C -->|failed| E[hard_failure naming the signon step]
    C -->|success| F[Replay target capability on same session]
    F --> G{Session expires mid-flow?}
    G -->|yes| H[Re-run signon once, retry the step]
    G -->|no| I[Continue normally]

Outcome taxonomy — outcomes.py

The take-home classified outcomes with _KNOWN_OUTCOMES, a dict hand-keyed per capability_id. That doesn't scale to covering a target's whole function surface — every new capability would need its own hand-written entries.

It's replaced by a per-target profile (classify(), reading meridian_outcomes.yaml) applied automatically to every step of every capability whose target matches. It uses two signals captured live during replay: the main document's HTTP status (from a page.on("response") listener on the real network response), and a substring match against the rendered HTML — checked first, because MERIDIAN returns an identical 400 for two different business meanings ("source share on hold" versus "insufficient funds") and the status code alone would collapse them.

Using status alone loses distinctions MERIDIAN deliberately overloads. Having an LLM read the error page would break the "replay never guesses" guarantee. Full-page structural diffing is more complex and more fragile than a targeted match on specific, verified error text. Both signals are read per request, so a fault injected mid-run is caught on the same request, with no polling delay.

flowchart TD
    A[Step fails or errors] --> B{Body text matches a known condition?}
    B -->|yes| C[Use that specific classification/code]
    B -->|no| D{HTTP status in the map?}
    D -->|yes| E[Use status-based classification]
    D -->|no| F[hard_failure]
A real find here

One match condition deliberately avoids the exact phrase "SUPERVISOR OVERRIDE REQUIRED", because that string is also a static warning shown to authorised supervisors — matching it would have wrongly denied an authorised action. Caught by reading the real page, not by assuming.

Generalize — meridian_flows.py

A scripted pass turns one concrete discovery recording into a reusable, parameterised capability — the member ID in the URL becomes a template, recorded literals become typed parameters, and risk level, required role, and checkpoint are set.

Honest limit: two of the seven capabilities needed one hand-added step each. Two near-identical dropdowns on the same form confused the discovery loop's decision-making; both appended steps are documented where they occur.

flowchart TD
    A[Raw discovery recording, concrete literals] --> B[generalize]
    B --> C[URL to member_id template]
    B --> D[Literals to typed params]
    B --> E[risk_level + requires_role + checkpoint set]
    C & D & E --> F[Reusable Capability]

API + chatbot + dashboard

The callable surface: capabilities exposed as a typed API, a thin chatbot that maps plain English to a capability plus arguments, and a server-rendered dashboard of run history.

There is deliberately no confirm field on the invoke endpoint — the chatbot has no way to self-approve an irreversible action. A risky capability runs to its confirmation checkpoint, pauses, and routes to the operator console; every run is written to runs.jsonl, redacted, and shown on the dashboard.

flowchart TD
    A[Chatbot: plain-English request] --> B[Claude maps to a capability + args]
    B --> C[POST /api/capabilities/id/invoke]
    C --> D{Risky?}
    D -->|yes| E[Runs to confirmation checkpoint, pauses, routes to operator console]
    D -->|no| F[Runs to completion]
    E --> G[Human approves/declines]
    G --> H[Result written to runs.jsonl, redacted]
    F --> H
    H --> I[Dashboard shows it]

What could change next

The cross-cutting limitations, kept short. None are architectural.

  • Two of seven MERIDIAN capabilities needed one hand-added step each (ambiguous dropdown forms confused the discovery loop).
  • Only one task runs at a time; concurrent requests queue.
  • No promotion gate yet on locator drift — the signal is recorded, nothing acts on it automatically.
  • Sensitive values are redacted before disk but not yet before being sent to the LLM during discovery.
  • The run registry is a flat JSONL file; SQLite would give the dashboard real queries instead of a full-file scan.
  • Encryption at rest is built and tested but not wired into the evidence write path; the dashboard has no auth (synthetic data only).
  • The perception seam is proven across two web targets, not beyond the browser — no desktop / OS-level adapter exists yet.

Appendix — full script reference

Not narrated top to bottom. Reference only — jump here if asked "what scripts do you have." Each card is written to be read aloud if grilled on a specific script.

scripts/run_discovery.py — the live "teach it a new task" entry point.

Why built this way: takes a goal string and a target URL as CLI args, nothing more — no config file, no separate goal-authoring format. Keeps the barrier to trying a new task at zero.

Defend: a thin CLI wrapper around run_discovery() means the actual logic lives in one testable function, not scattered across argument-parsing code — the script itself is almost entirely plumbing.

Honest limitation: no validation of the goal string's quality before spending real API calls on it — a vague or contradictory goal just runs until max_steps or timeout and reports a non-obvious failure. A production version would want a cheap pre-flight check.

scripts/run_replay.py — the "run it in production" entry point.

Why built this way: mirrors run_discovery.py's CLI shape deliberately — capability path in, params in, result out — so the two commands feel like the same tool used at two different points in a task's life, not two unrelated pieces of software.

Defend: takes params as a raw JSON string on the command line rather than a config file — for a demo/CLI context this is the fastest path from "I have an idea" to "it ran," and matches how the API layer's invoke endpoint accepts args too, so the mental model transfers.

Honest limitation: a malformed JSON param string fails with a fairly raw Python traceback, not a friendly error — fine for a demo, not fine for a real operator-facing tool.

scripts/demo_guardrail_violation.py — deliberately triggers the allowlist to prove it blocks.

Why built this way: rather than just asserting "the allowlist works" in prose, this actually attempts a disallowed action and shows GuardrailViolation firing — the difference between a claim and a demonstration.

Defend: this is the fastest, lowest-risk way to prove a negative (something doesn't happen) — running it takes seconds, no browser, no API key needed.

Honest limitation: it only proves the allowlist blocks one specific disallowed thing — it's a targeted proof, not a fuzz test across every possible disallowed action.

scripts/demo_encryption_at_rest.py — encrypts a fake sensitive record, proves round-trip.

Why built this way: writes a customer-shaped fake record to a real file, shows it's unreadable garbage without the key, then decrypts it back byte-for-byte identical — proves both directions, not just "encryption ran."

Defend: this is what justifies claiming the encryption module is "proven independently" even though it's not wired into the actual evidence-writing paths — the module itself is genuinely tested, the integration point is the separate, honestly-named cut.

Honest limitation: uses one static key from an environment variable — this script proves the crypto is correct, not that the key-management story is production-ready. Say that distinction out loud if asked, don't let "proven" imply more than it does.

scripts/demo_escalation.py — runs a task designed to trigger human hand-off.

Why built this way: deliberately picks a goal that's expected to hit a risky checkpoint, so the escalation path is exercised on demand rather than hoping a random discovery run happens to need it.

Defend: walks through both branches — approve and decline — so it's a complete proof of the mechanism, not just the happy path.

Honest limitation: this is a scripted trigger of escalation, not a proof that escalation fires correctly on every possible risky scenario — the risk-detection logic itself is tested more broadly elsewhere (the discovery loop's own dead-end/risk checks); this script proves the hand-off mechanism works once it's triggered.

scripts/verify_perception_live.py — snapshots a real page, checks specific things are visible.

Why built this way: this is the actual script that caught the iframe gap — it exists specifically to check assumptions against reality rather than trusting documentation or memory of how an API used to behave.

Defend: this is the single best answer to "how do you know your perception layer actually works" — not "I tested it once," but "here's a script that re-verifies it against the live page any time I need to check."

Honest limitation: it checks specific, hand-picked assertions (does this string appear, is this role present) — it's not a general perception correctness test, it's a targeted regression check for the specific gaps that were once found.

scripts/smoke_test_table_position.py — targeted test for the 4th, most unusual locator tier.

Why built this way: the table-position tier is the least like the other three (it addresses by row/column index instead of identity), so it gets its own dedicated test rather than being folded into a general locator test.

Honest limitation: only covers the specific table shape (headers present, no per-row label) the take-home's transaction list actually has — a differently-structured data table might need a different addressing scheme entirely, untested here.

scripts/discover_all_meridian.py — real LLM discovery run for every MERIDIAN function.

Why built this way: one script, one dict (RUNS) mapping each of the 7 functions to its target URL and goal — running python scripts/discover_all_meridian.py with no args does all 7 in sequence; passing specific flow names runs a subset, useful when re-discovering just one after a change.

Defend: backs up existing capabilities to /tmp before overwriting, and a dead-ended or timed-out run leaves the current capability in place rather than clobbering a working one with a failed attempt — a small but real safety net around the exact save_capability() overwrite gap named elsewhere as an open issue.

Honest limitation: the backup is to /tmp, not version control — it protects against a single bad re-run, not against needing to roll back after the fact once something else has already run.

scripts/run_meridian.py — the MERIDIAN version of run_replay.py, session-aware.

Why built this way: wraps run_with_session() instead of calling replay() directly, plus an --inject flag most other replay scripts don't have — because MERIDIAN specifically needs both a live session and a live way to force a runtime fault for demo purposes.

Honest limitation: --inject talks to MERIDIAN's own fault-injection query parameter — it only works against this specific target's testing feature, it's not a general fault-injection mechanism this project built.

scripts/meridian_scout.py — checks which member/share IDs are safe to use right now.

Why built this way: the hosted target is stateful in memory and only resets on redeploy, so running a risky demo command against stale assumptions (a share that's since gone on hold, a balance that's already too low) would fail for reasons that have nothing to do with the system being demoed.

Defend: this is operational awareness of a target you don't control, built as a real tool rather than "hope the demo data is still fine" — worth explicitly calling out as a deliberate, non-obvious addition in the interview, since it wasn't asked for by the brief.

Honest limitation: only as current as the moment it's run — if the state changes between scouting and demoing (another candidate using the same shared hosted target, for instance), it can go stale within the same session.

scripts/meridian_inject.py — out-of-band control of MERIDIAN's fault-injection settings.

Why built this way: explicitly test/demo infrastructure, not something any capability itself does — kept as a separate script specifically so it's obvious this isn't part of the production automation surface.

Defend: the allowlist's /settings block (guardrails) means the automation can never reach this control panel — this script bypasses that only because it's a human-run operator tool, not because the guardrail has a hole in it. Worth stating precisely if asked "wait, doesn't this contradict your blocked-route claim" — it doesn't, because this script isn't part of any capability's replay path.

record_meridian_signon.py, record_meridian_flow.py, record_meridian_transfer.py — scripted (non-LLM) recorder fallbacks.

Why built this way: for fixed, non-branching forms (a form → review → post, no decision to discover), the position was that spending a real LLM discovery run on it — including risking a real irreversible POST during recording — was a poor trade once the discovery loop was already proven on meridian_check_member_balance.

Defend: the brief itself explicitly allows this: "if you can't get live LLM or browser access working for part of the flow, mock that boundary cleanly and document it." This is exactly that seam, and it's documented, not hidden.

Honest limitation, be precise if asked: the currently-committed capability files were NOT actually produced by these scripts — verified directly, every committed meridian_*.v1.json has a created_from_run_id pointing to a real discovery_run_*.jsonl transcript. These scripts are a real, working fallback path that exists and could be used again, but they are not what generated what's in the repo right now.

scripts/smoke_meridian_signon.py — live proof the label-based locator works end to end.

Why built this way: proves the whole new-tier mechanism in one script — perception derives a name, the recorder builds a labeled_field step, execution actually logs in, and replaying the compiled capability reaches the menu again, deterministically.

Honest limitation: proves it works for the sign-on form specifically — it's the strongest single proof available, but it's one form, not a proof across every MERIDIAN form's label layout.

scripts/smoke_meridian_session.py — live proof a session carries over between two capabilities.

Why built this way: specifically tests the thing that could subtly fail silently — that the MC_SID cookie genuinely persists across two separate replay() calls on the same Playwright page object, with no re-login in between.

Honest limitation: tests the successful case; the reauth-on-expiry path (Sessions) has its own separate coverage, not exercised by this particular script.

scripts/demo_meridian_escalation.py — fully scripted, real-browser MERIDIAN escalation proof.

Why built this way: real browser, real separate operator process, real HTTP between them — no mocking, matching the same "verify against reality" discipline as everything else in this project.

Honest limitation: scripted means the specific escalation trigger is chosen in advance, not discovered live — it proves the mechanism works, not that every real risky MERIDIAN action would organically trigger it during a live, undirected discovery run.
