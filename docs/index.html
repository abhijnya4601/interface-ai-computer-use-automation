Discover once, replay forever

An AI learns a banking task once, by actually doing it — then the system replays that exact recipe forever, deterministically, with zero AI involved after that first run.

Built for interface.ai — the take-home core, then adapted live against MERIDIAN CORE.

Act 1

The take-home core

Eight modules. Each one: what it is, the exact tool it uses, why that tool and not the obvious alternative, a flowchart of its control flow, the scripts that exercise it, and — where there was one — a real bug found while building it.

Perception

What it is: turns the live webpage into a structured description the AI can reason about — not a screenshot, a semantic tree of roles and names.

page.locator("html").aria_snapshot() a Playwright API that walks the browser's own accessibility tree — the same structured tree a screen reader uses for a blind user — and returns it as YAML: every element's role (button, textbox, link…), its accessible name, its current value, and its children, in document order. It is not something this project built; it's a standard browser capability Playwright exposes.

Why this approach, against the real alternatives

AlternativeWhy not chosen
Screenshot + vision model reading pixels Coordinates break the instant a page shifts, resizes, or restyles; a vision model has to infer what a shape means instead of reading a declared identity.
Raw DOM query (document.querySelectorAll) + custom heuristics Reinvents what the accessibility tree already computes for free — role, name, and state are already resolved by the browser's own accessibility engine, correctly, including ARIA overrides.
Fixed pixel / coordinate automation (record-and-replay tools like Sikuli) Zero resilience to any visual change at all — the weakest possible option for a target expected to be updated over time.

Real-time and unclear-DOM behavior: aria_snapshot() is a live, synchronous call against whatever the page currently renders — it reflects dynamic content, JS-rendered elements, and in-progress state changes at the moment it's called, not a cached or precomputed structure. It degrades gracefully on messy markup too: an element with no explicit ARIA role still gets an implicit role from its HTML tag (a <button> is role button even with zero ARIA attributes added), which is exactly why it handles ordinary messy-but-semantic HTML far better than a brittle CSS-selector scraper would. Its real limit — not a strength — is elements with no name at all, which is precisely the MERIDIAN problem in Act 2.

flowchart TD
    A[Live page] --> B[aria_snapshot]
    B --> C{Any iframes?}
    C -->|no| E[role/name tree]
    C -->|yes| D[Snapshot each frame separately, graft in as synthetic Iframe node]
    D --> E
    E --> F[Passed to discovery loop as observation]

Real bug found here

The spec called for page.accessibility.snapshot(); it no longer exists in the Playwright version used. The replacement, aria_snapshot(), was verified directly against a live page and found to not reach inside iframes at all — confirmed by testing, not assumed. Fixed by snapshotting each iframe separately and grafting the result in under a synthetic node, deliberately capitalized (Iframe) so nothing downstream mistakes it for a real accessibility role the page declared.

Discovery loop

What it is: the live loop where an AI is given a goal in plain English and figures out, step by step, how to complete it — perceive, decide, act, repeat.

Tool used: Claude, via the Anthropic API.

Why this tool: real judgment is needed here — "there are two Continue buttons, which one" is not something you can hardcode.

Why not hardcode the steps yourself: it would need to be rewritten for every task and would break the instant the page changed even slightly. Letting the AI discover the steps means it adapts to a page it's never seen.

flowchart TD
    A[Goal + observation] --> B[Claude decides next action]
    B --> C[guardrail_check before executing]
    C -->|blocked| X[GuardrailViolation, halt]
    C -->|allowed| D[Execute via agent/tools.py]
    D --> E[Recorder logs the step inline]
    E --> F{Finished, max_steps, timeout, or dead-end?}
    F -->|no| A
    F -->|dead-end detected| G[Auto-escalate to human]
    F -->|yes| H[Discovery complete]

The wall-clock timeout originally kept counting during an escalation wait, so a human's own thinking time could burn through the run's timeout budget. Fixed by shifting the start time forward by however long the escalation actually took, so only real working time counts against the limit.

Recorder

What it is: runs inline during discovery, writing down each accepted action as a precise step — including how it found the element, not just what it did.

Tool used: custom Python — a 4-tier fallback locator builder.

Why 4 tiers: real pages aren't uniformly well-labeled; a single rigid strategy fails outright on cases the weaker tiers exist for.

Why not just always use the strongest match: it doesn't always exist — some elements have no unique name, so a ladder of fallback options beats an all-or-nothing rule.

flowchart TD
    A[Element to record] --> B{role+name match count}
    B -->|exactly 1| C[Tier: role_name]
    B -->|more than 1| D[Tier: structural - first match]
    B -->|0| E[Tier: text - raw text match]
    F[Special case: table cell, no per-row label] --> G[Tier: table_position]
    C & D & E & G --> H[Logged to tier_log - the drift signal]

Parameter detection originally used substring matching against the goal text — this once caused a $50 deposit amount to get mistaken for a member ID, because "50" also appeared elsewhere in the goal string. Fixed by requiring an exact match instead of a substring match.

Capability schema

What it is: the actual file format for a saved recipe — typed, versioned, structured JSON, not code.

Tool used: Pydantic.

Why this tool: guarantees the file can't be malformed — a missing or wrong-typed field errors immediately instead of silently corrupting data later.

Why not a plain dict: a bare dict lets anything through unchecked; in a banking system, a silently malformed artifact is a much worse failure than an immediate, loud validation error.

flowchart TD
    A[Capability] --> B[Steps list]
    B --> C[LocatorTarget: strategy + reasoning - required, not optional]
    B --> D[ExpectedOutcome: business_outcome / recoverable / hard_failure]
    A --> E[risk_level: safe or risky]
    A --> F[input_schema / output_schema]

Scripts for this module: none directly — this is a schema file (artifact/schema.py), not a runnable script.

Compiler

What it is: finalizes a raw recording into the schema, and attaches known business-outcome rules from actually exploring the app — not just what one lucky/unlucky discovery run happened to hit.

Tool used: custom Python (agent/compiler.py).

Why declare outcomes here instead of guessing at replay time: replay should never interpret a page live — it should already know, from someone who explored the app, what each outcome means.

flowchart TD
    A[Raw recorded steps] --> B[Attach known outcome rules per step]
    B --> C[save_capability writes capabilities/id.vN.json]
Real bug found here

An outcome was originally declared on the wrong step — assumed a locked-member denial happened at the "Continue" click, when the app actually never renders that link at all for a locked member, one click earlier. Found by replaying every declared outcome against the real app, not by trusting the original assumption.

Replay engine

What it is: runs a saved recipe against new input, deterministically, with zero AI calls.

Tool used: Playwright again, no LLM import anywhere in this module.

Why deterministic replay instead of AI-driven-every-time: the entire point of the architecture — same input, same behavior, every time, fast, free of AI cost or unpredictability.

flowchart TD
    A[Step to execute] --> B[Try tier 1: role_name]
    B -->|fail| C[Try tier 2: structural]
    C -->|fail| D[Try tier 3: text]
    D -->|fail| E[Try tier 4: table_position, if applicable]
    E -->|fail| F[No element found]
    B -->|found| G[Execute action]
    C -->|found| G
    D -->|found| G
    E -->|found| G
    G --> H{Check declared expected_outcomes}
    F --> H
    H -->|matched, business| I[Result: business_outcome]
    H -->|matched, recoverable| J[Result: recoverable_handled]
    H -->|no match, checkpoint verified| K[Result: success]
    H -->|no match, nothing verified| L[Result: hard_failure + screenshot]

Guardrails

What it is: three independent safety mechanisms — an allowlist checked before every action, a redaction pass before anything is written to disk, and real encryption at rest.

Tool used: custom Python + the cryptography library for encryption.

Why not build custom encryption: rolling your own cryptography is one of the most common, dangerous mistakes in security — always use an audited standard library.

flowchart TD
    A[Proposed action] --> B{Domain allowed?}
    B -->|no| X1[GuardrailViolation, halt]
    B -->|yes| C{Action type allowed?}
    C -->|no| X1
    C -->|yes| D{Route blocked?}
    D -->|yes| X1
    D -->|no| E[Action proceeds]
    E --> F[Result about to be written]
    F --> G[redact by key name]
    G --> H[redact by value shape]
    H --> I[encrypt_at_rest, if configured]
    I --> J[Written to evidence/]

Escalation

What it is: a hand-off mechanism — risky or stuck situations pause and wait for a real human to approve or decline before anything irreversible happens.

Tool used: a shared lease file plus a separate Flask console for the human reviewer.

Why not let the AI decide everything: some actions are irreversible; a bank cannot let an AI make that call alone.

flowchart TD
    A[Risky checkpoint or dead-end] --> B[Flip lease to human, screenshot + context saved]
    B --> C[Operator console shows context]
    C --> D{Human decision}
    D -->|approved| E[Flip lease back, resume same browser session]
    D -->|declined| F[Result: escalated, nothing committed]

Act 2

The MERIDIAN adaptation

Point the same core at a real, messy legacy target — web-sample.interface-hiring.com — cover its full function surface, and wrap it as a callable API a chatbot drives and a dashboard shows. The schema didn't change. Six modules.

The blocker

What exactly broke, named precisely: aria_snapshot() (Perception) still runs perfectly fine against MERIDIAN — it's a live, standard browser API, nothing about the target breaks it mechanically. What breaks is what it returns: MERIDIAN's forms are <td class="lbl">Amount:</td><td><input name="amt"></td> — a label sitting in a neighboring table cell, with zero programmatic association (<label for>, aria-label, aria-labelledby) to the input next to it. The browser's accessibility engine has nothing to compute a name from, so the snapshot correctly and honestly reports the input as an unnamed - textbox. Nothing needed to be replaced in Perception — perception itself didn't change. What broke is one layer downstream: the take-home's locator tiers 1–2 (agent/recorder.py::build_locator, replay/engine.py::_locate), which are built entirely around "role plus name resolves to something."

Confirmed live, not assumed: ran aria_snapshot() against the real sign-on page and counted matches for get_by_role("textbox", name="Operator ID") — zero, against a page with a visibly obvious "Operator ID" field sitting right there for a human. That gap between what a human sees instantly and what the accessibility tree can name is the entire adaptation problem in one sentence.

Why not the other obvious fixes, each considered and rejected

AlternativeWhy not chosen
Fall back to screenshots + a vision model just for MERIDIAN Reintroduces exactly the fragility the accessibility-tree approach was chosen to avoid in Act 1 — pixel coordinates on a table-based legacy layout are the worst case for that approach, not a reasonable exception.
Hardcode CSS selectors per MERIDIAN field Not automation-adaptive at all — brittle to any markup change, and defeats the entire "discover it, don't hand-write it" premise of the whole project.
Ask MERIDIAN's maintainers to add proper labels Not a real option against a fixed legacy target you don't control — the whole point of this category of problem is that you can't change the app.

Real-time / unclear-DOM behavior of the actual fix (previewed here, detailed next): the replacement runs as a live in-page JS evaluation on every observation — same synchronous, live-DOM guarantee as aria_snapshot() itself, not a precomputed or cached label map — so it correctly tracks a table row's current content even as different members' data loads into it.

flowchart TD
    A[MERIDIAN input field] --> B[aria_snapshot - unchanged, still live]
    B --> C[Unnamed textbox - browser has nothing to name it from]
    C --> D[Tier 1 role_name: 0 matches]
    D --> E[Tier 2 structural: 0 matches]
    E --> F[Perception itself is fine - the locator ladder needs new rungs]

New locator tiers — legacy_locate.py

What was actually added, precisely: two new functions slotted into the existing fallback ladder as tiers 3 and 4 — nothing in tiers 1–2, the schema, or the replay engine's control flow was rewritten; this is strictly additive.

Tier 3 — derive_unnamed_field_labels() + locate_labeled_field()

  • What it is: a small JS snippet, run live in the page context via Playwright's page.evaluate(), that walks every form control with no native accessible name and looks at what's physically next to it — a labeled table cell in the same row, first; a preceding cell's text, second; a non-associated <label> element, third. The derived label is then matched back to a specific element using an XPath predicate that normalizes whitespace and strips a leading * / trailing : so "Operator ID:" and "Operator ID" match the same control.
  • Why in-page JS rather than parsing the DOM after the fact in Python: it needs to walk live DOM relationships (closest(), previousElementSibling) exactly the way a human visually reads a table row — cheaper and more direct to compute inside the browser than to reconstruct those relationships after serializing the whole tree out to Python.
  • Why not train a small ML model to guess labels from visual layout: far more complex to build and validate for a one-target adaptation sprint, non-deterministic (the antithesis of everything replay is trying to guarantee), and unnecessary — the actual page structure already contains the answer deterministically, it's just not exposed through the standard accessible-name computation.
  • Real-time / unclear-DOM behavior: runs fresh on every observation, so it always reflects the row currently on screen — correct for a different member's data loading into the exact same table structure. It explicitly refuses to guess on ambiguity: if a label candidate resolves to more than one matching control, it's skipped in favor of the next, looser candidate rather than picked arbitrarily — same "never silently guess" discipline as every other tier.

Tier 4 — locate_field_name()

  • What it is: resolves a control by its raw HTML name= attribute — the literal field name the server-rendered form submits.
  • Why this counts as a legitimate tier and not a hack: on a server-rendered legacy app, the name= attribute is the actual HTTP form contract the backend requires to function — it is load-bearing plumbing the app cannot work without, not a test-only convenience.
  • Why ranked last despite arguably being the most stable of all four: it's opaque to a human reviewer — name="amt" means nothing on its own without cross-referencing the live page, which breaks the artifact's whole reviewability principle (the schema's reasoning field). The ranking optimizes for human-clarity first, mechanical stability second.
flowchart TD
    A[Unnamed control] --> B[Tier 3: labeled_field - nearest label cell/text]
    B -->|ambiguous or none| C[Tier 4: field_name - the HTML name attribute]
    C -->|ambiguous or none| D[Tier 5: table_position / text, same as take-home]
    B -->|exactly 1 match| E[Resolved, logged to tier_log same as every other tier]
    C -->|exactly 1 match| E

Outcome taxonomy — outcomes.py

What had to go: the take-home's _KNOWN_OUTCOMES — a dict hand-keyed by capability_id, authored per capability. It doesn't scale to "cover a target's full function surface" the brief asks for; every new capability would need its own manually written entries.

What replaced it, and how it actually works: a per-target profile (classify(), reading meridian_outcomes.yaml), applied automatically to every step of every capability whose target matches, using two real, checkable signals captured live during replay:

  1. The main-frame document's HTTP status code — captured via a page.on("response") listener on the actual network response, not inferred or guessed from page content.
  2. A substring match against the rendered page's HTML (page.content()) — checked before the status-code map, because MERIDIAN returns the identical HTTP 400 for two genuinely different business meanings ("source share is on hold" vs "insufficient funds"); status code alone would collapse both into one vague, less useful answer.

Why not other approaches, considered and rejected

AlternativeWhy not chosen
Only use HTTP status, ignore body content Loses real distinctions MERIDIAN specifically overloads onto one status code — a strictly worse signal for this target.
Use an LLM to interpret the error page live, during replay Breaks the entire "replay never guesses, never calls an LLM" guarantee that's the whole architecture's premise.
Full-page structural diffing against a known-good page Far more complex to build and more fragile to incidental layout changes than a targeted substring check against specific, verified error text.

Real-time / unclear-DOM behavior: both signals are captured live, per request, during the actual replay run — not precomputed or cached — so a fault forced mid-run via ?inject= is detected the same request it occurs on, with no polling delay.

flowchart TD
    A[Step fails or errors] --> B{Body text matches a known condition?}
    B -->|yes| C[Use that specific classification/code]
    B -->|no| D{HTTP status in the map?}
    D -->|yes| E[Use status-based classification]
    D -->|no| F[hard_failure]
A real find here

One match condition deliberately avoids the exact phrase "SUPERVISOR OVERRIDE REQUIRED" because that string is also a static warning shown to authorized supervisors — matching it would have wrongly denied an authorized action. Caught by reading the real page, not by assuming.

Cuts & what's next

  • Two of seven MERIDIAN capabilities needed one hand-added step each (ambiguous dropdown forms confused the discovery loop).
  • Only one task runs at a time; concurrent requests queue.
  • No promotion gate yet on locator-drift — the signal exists, nothing acts on it automatically.
  • Sensitive values aren't yet redacted before being sent to the LLM during discovery, only before being written to disk.
  • Dashboard has no authentication (synthetic demo data only).
  • A real desktop / OS-level perception adapter doesn't exist — the seam is proven across two web targets, not proven beyond the browser yet.

Appendix — full script reference

Not narrated top to bottom. Reference only — jump here if asked "what scripts do you have." Each card is written to be read aloud verbatim if grilled on a specific script.

scripts/run_discovery.py — the live "teach it a new task" entry point.

Why built this way: takes a goal string and a target URL as CLI args, nothing more — no config file, no separate goal-authoring format. Keeps the barrier to trying a new task at zero.

Defend: a thin CLI wrapper around run_discovery() means the actual logic lives in one testable function, not scattered across argument-parsing code — the script itself is almost entirely plumbing.

Honest limitation: no validation of the goal string's quality before spending real API calls on it — a vague or contradictory goal just runs until max_steps or timeout and reports a non-obvious failure. A production version would want a cheap pre-flight check.

scripts/run_replay.py — the "run it in production" entry point.

Why built this way: mirrors run_discovery.py's CLI shape deliberately — capability path in, params in, result out — so the two commands feel like the same tool used at two different points in a task's life, not two unrelated pieces of software.

Defend: takes params as a raw JSON string on the command line rather than a config file — for a demo/CLI context this is the fastest path from "I have an idea" to "it ran," and matches how the API layer's invoke endpoint accepts args too, so the mental model transfers.

Honest limitation: a malformed JSON param string fails with a fairly raw Python traceback, not a friendly error — fine for a demo, not fine for a real operator-facing tool.

scripts/demo_guardrail_violation.py — deliberately triggers the allowlist to prove it blocks.

Why built this way: rather than just asserting "the allowlist works" in prose, this actually attempts a disallowed action and shows GuardrailViolation firing — the difference between a claim and a demonstration.

Defend: this is the fastest, lowest-risk way to prove a negative (something doesn't happen) — running it takes seconds, no browser, no API key needed.

Honest limitation: it only proves the allowlist blocks one specific disallowed thing — it's a targeted proof, not a fuzz test across every possible disallowed action.

scripts/demo_encryption_at_rest.py — encrypts a fake sensitive record, proves round-trip.

Why built this way: writes a customer-shaped fake record to a real file, shows it's unreadable garbage without the key, then decrypts it back byte-for-byte identical — proves both directions, not just "encryption ran."

Defend: this is what justifies claiming the encryption module is "proven independently" even though it's not wired into the actual evidence-writing paths — the module itself is genuinely tested, the integration point is the separate, honestly-named cut.

Honest limitation: uses one static key from an environment variable — this script proves the crypto is correct, not that the key-management story is production-ready. Say that distinction out loud if asked, don't let "proven" imply more than it does.

scripts/demo_escalation.py — runs a task designed to trigger human hand-off.

Why built this way: deliberately picks a goal that's expected to hit a risky checkpoint, so the escalation path is exercised on demand rather than hoping a random discovery run happens to need it.

Defend: walks through both branches — approve and decline — so it's a complete proof of the mechanism, not just the happy path.

Honest limitation: this is a scripted trigger of escalation, not a proof that escalation fires correctly on every possible risky scenario — the risk-detection logic itself is tested more broadly elsewhere (the discovery loop's own dead-end/risk checks); this script proves the hand-off mechanism works once it's triggered.

scripts/verify_perception_live.py — snapshots a real page, checks specific things are visible.

Why built this way: this is the actual script that caught the iframe gap — it exists specifically to check assumptions against reality rather than trusting documentation or memory of how an API used to behave.

Defend: this is the single best answer to "how do you know your perception layer actually works" — not "I tested it once," but "here's a script that re-verifies it against the live page any time I need to check."

Honest limitation: it checks specific, hand-picked assertions (does this string appear, is this role present) — it's not a general perception correctness test, it's a targeted regression check for the specific gaps that were once found.

scripts/smoke_test_table_position.py — targeted test for the 4th, most unusual locator tier.

Why built this way: the table-position tier is the least like the other three (it addresses by row/column index instead of identity), so it gets its own dedicated test rather than being folded into a general locator test.

Honest limitation: only covers the specific table shape (headers present, no per-row label) the take-home's transaction list actually has — a differently-structured data table might need a different addressing scheme entirely, untested here.

scripts/discover_all_meridian.py — real LLM discovery run for every MERIDIAN function.

Why built this way: one script, one dict (RUNS) mapping each of the 7 functions to its target URL and goal — running python scripts/discover_all_meridian.py with no args does all 7 in sequence; passing specific flow names runs a subset, useful when re-discovering just one after a change.

Defend: backs up existing capabilities to /tmp before overwriting, and a dead-ended or timed-out run leaves the current capability in place rather than clobbering a working one with a failed attempt — a small but real safety net around the exact save_capability() overwrite gap named elsewhere as an open issue.

Honest limitation: the backup is to /tmp, not version control — it protects against a single bad re-run, not against needing to roll back after the fact once something else has already run.

scripts/run_meridian.py — the MERIDIAN version of run_replay.py, session-aware.

Why built this way: wraps run_with_session() instead of calling replay() directly, plus an --inject flag most other replay scripts don't have — because MERIDIAN specifically needs both a live session and a live way to force a runtime fault for demo purposes.

Honest limitation: --inject talks to MERIDIAN's own fault-injection query parameter — it only works against this specific target's testing feature, it's not a general fault-injection mechanism this project built.

scripts/meridian_scout.py — checks which member/share IDs are safe to use right now.

Why built this way: the hosted target is stateful in memory and only resets on redeploy, so running a risky demo command against stale assumptions (a share that's since gone on hold, a balance that's already too low) would fail for reasons that have nothing to do with the system being demoed.

Defend: this is operational awareness of a target you don't control, built as a real tool rather than "hope the demo data is still fine" — worth explicitly calling out as a deliberate, non-obvious addition in the interview, since it wasn't asked for by the brief.

Honest limitation: only as current as the moment it's run — if the state changes between scouting and demoing (another candidate using the same shared hosted target, for instance), it can go stale within the same session.

scripts/meridian_inject.py — out-of-band control of MERIDIAN's fault-injection settings.

Why built this way: explicitly test/demo infrastructure, not something any capability itself does — kept as a separate script specifically so it's obvious this isn't part of the production automation surface.

Defend: the allowlist's /settings block (guardrails) means the automation can never reach this control panel — this script bypasses that only because it's a human-run operator tool, not because the guardrail has a hole in it. Worth stating precisely if asked "wait, doesn't this contradict your blocked-route claim" — it doesn't, because this script isn't part of any capability's replay path.

record_meridian_signon.py, record_meridian_flow.py, record_meridian_transfer.py — scripted (non-LLM) recorder fallbacks.

Why built this way: for fixed, non-branching forms (a form → review → post, no decision to discover), the position was that spending a real LLM discovery run on it — including risking a real irreversible POST during recording — was a poor trade once the discovery loop was already proven on meridian_check_member_balance.

Defend: the brief itself explicitly allows this: "if you can't get live LLM or browser access working for part of the flow, mock that boundary cleanly and document it." This is exactly that seam, and it's documented, not hidden.

Honest limitation, be precise if asked: the currently-committed capability files were NOT actually produced by these scripts — verified directly, every committed meridian_*.v1.json has a created_from_run_id pointing to a real discovery_run_*.jsonl transcript. These scripts are a real, working fallback path that exists and could be used again, but they are not what generated what's in the repo right now.

scripts/smoke_meridian_signon.py — live proof the label-based locator works end to end.

Why built this way: proves the whole new-tier mechanism in one script — perception derives a name, the recorder builds a labeled_field step, execution actually logs in, and replaying the compiled capability reaches the menu again, deterministically.

Honest limitation: proves it works for the sign-on form specifically — it's the strongest single proof available, but it's one form, not a proof across every MERIDIAN form's label layout.

scripts/smoke_meridian_session.py — live proof a session carries over between two capabilities.

Why built this way: specifically tests the thing that could subtly fail silently — that the MC_SID cookie genuinely persists across two separate replay() calls on the same Playwright page object, with no re-login in between.

Honest limitation: tests the successful case; the reauth-on-expiry path (Sessions) has its own separate coverage, not exercised by this particular script.

scripts/demo_meridian_escalation.py — fully scripted, real-browser MERIDIAN escalation proof.

Why built this way: real browser, real separate operator process, real HTTP between them — no mocking, matching the same "verify against reality" discipline as everything else in this project.

Honest limitation: scripted means the specific escalation trigger is chosen in advance, not discovered live — it proves the mechanism works, not that every real risky MERIDIAN action would organically trigger it during a live, undirected discovery run.
