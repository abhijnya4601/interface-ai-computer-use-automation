The parts you don't see in one run

Every panel above is driven by real captured output from the repo. These are the other things the system does with a capability once it exists - safety, reuse, and the numbers a team watches in production.

Left of the seam - runs once

  • An LLM drives an observe → decide → act loop over the live page
  • Every accepted action becomes a typed Step as it happens
  • The model proposes the branches & value shapes it can see
  • Non-deterministic. Reviewed by a human before it ships.
the Capability artifact

Right of the seam - runs every time

  • A deterministic engine walks the recorded Steps
  • No model call - branches are decided by literal page checks
  • Outcomes: success · business outcome · data unavailable · hard failure
  • Same allowlist & redaction as discovery; a lease can pause it for a human

Redaction knows where the data is going

guardrails/pii.py · sink-aware

“Redact names: yes/no” is the wrong question - a customer name in a capability's declared output is the point; the same name in a prompt sent to a third-party model is a leak. So the same observation is redacted differently per destination.

One capability, many tenants

artifact/patch.py · base + per-tenant patch

Most tenants running the same product replay the base capability unchanged. A tenant whose UI differs gets a small patch applied over the base - not a separate artifact. Verified live against a variant that relabels one row header.

When it stops for a human

        
escalation/ · a file-backed lease

        
A state-changing final step (open an account, file a dispute) is never taken by the agent. It fills and reviews the form, then flips a lease to human and blocks - the same live browser session a person takes over - until a real HTTP approve/decline comes back. Try the open-sub-account task above to see it in the run.
